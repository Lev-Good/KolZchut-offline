# הוראות להפצה בפורום "מתמחים טופ"

מסמך זה מכיל הוראות מעשיות להפצת פרויקט `KolZchut-offline` עם מערכת העדכונים המבוזרת (PR + auto-merge).

## 1. מטרת ההפצה

למשוך מספר מצומצם של משתמשים אמינים שיכולים לעדכן את הארכיון באופן מבוזר דרך המחשבים שלהם. עדכון יפורסם אוטומטית לכל המשתמשים לאחר בדיקות תקינות, ללא אישור ידני וללא תלות במחשב/שרת של המפתח.

## 2. עיקרי המערכת
- עדכנים מורשים פועלים באמצעות חשבון GitHub אישי.
- כל עדכון נעשה ע"י `kolzchut_contribute.py` שיוצר branch נפרד ו-Pull Request עם תגית `auto-merge-candidate`.
- בדיקות אוטומטיות ב-GitHub Actions (PR-check): שלמות ארכיון, תקינות index.json, סינון, אימות מחיקות, זיהוי אנומליות.
- אם כל הבדיקות עוברות — מיזוג אוטומטי ל-`master` והפעלת Release (יצירת ZIP מהארכיון המאוחד).
- אין דחיפה ישירה ל-`master`. הענף מוגן ב-Branch Protection/Rulesets.
- אין אסימונים משותפים בקוד — כל עדכן משתמש ב-GitHub credentials שלו.

## 3. הכנה לפני הפצת הפוסט

**בדיקות מקומיות:**
```bash
python -m py_compile kolzchut_*.py
python -c "import yaml; [yaml.safe_load(open(f)) for f in ['.github/workflows/pr-check.yml','.github/workflows/auto-merge.yml','.github/workflows/daily-sync.yml','.github/workflows/cloud-probe.yml']]"
python kolzchut_verify.py  # חייב להחזיר exit 0
```

**וודא:**
- master מוגן (branch protection) — לא ניתן לדחוף ישירות.
- `kolzchut_contribute.py`, `kolzchut_local_sync.py`, `kolzchut_verify.py` מעודכנים.
- התיעוד קיים: [docs/DISTRIBUTED_UPDATES.md](docs/DISTRIBUTED_UPDATES.md)
- [README.md](README.md) מעודכן ומסביר על הסנכרון המבוזר.

## 4. טקסט לפוסט בפורום "מתמחים טופ"

העתק/ערוך לפי הצורך את הטקסט הבא:

```text
KolZchut-offline — עדכונים מבוזרים אוטומטיים

שלום לכולם,

פרויקט KolZchut-offline (https://github.com/Lev-Good/KolZchut-offline) עבר לאחרונה למודל של עדכונים מבוזרים.

עכשיו מספר משתמשים מורשים יכולים לעדכן את המאגר המקומי שלהם ולפרסם את העדכון לכל המשתמשים באופן אוטומטי, לאחר בדיקות תקינות.

איך זה עובד:
- משתמש מורשה מריץ "בדוק עדכונים והגש לפרסום" (kolzchut_contribute.py).
- הסקריפט יוצר ענף נפרד + Pull Request ל-master.
- GitHub Actions בודק שלמות הארכיון, תקינות, סינון, מחיקות, התנגשות וכו'.
- אם הכל תקין — המיזוג קורה אוטומטי, וגרסה מעודכנת זמינה לכולם.

דרישות להצטרפות כעדכן מורשה:
- חשבון GitHub פעיל
- רצון לעזור לעדכן את הארכיון מעת לעת (סיוע קטן מספיק)
- הבנה בסיסית של שימוש ב-Terminal/סקריפטים Python (הסקריפט מפשט את התהליך)
- דיסקרטיות ואמון — העדכנים הם מצומצם מאוד

מוזמנים לפנות אליי בהודעה פרטית אם אתם מעוניינים להצטרף כעדכן מורשה.
אני אחבר אתכם לרשימת Collaborators בריפו עם ההרשאות המינימליות הדרושות, ואתן לכם הוראות קצרות להפעלה.
```

**טיפים לפרסום:**
- פרסם בסקטור המתאים בפורום (כלים, עזרה טכנית, או פרויקטים חופשיים). הימנע מפרסום כפול.
- אם הפורום מאפשר קישור — צרף את ה-Repo URL.
- אל תכלול אסימונים או מפתחות בקוד/הודעה.

## 5. קריטריונים לבחירת עדכנים מורשים

בחר בקפידה עדכנים בעלי מאפיינים אלה:

| קריטריון | הסבר | חשיבות |
|---|---|---|
| אמינות | פעיל בפורום זמן מה, ניכר בתגובות אחראיות | קריטי |
| מיקוד פרויקט | התעניין בעבר בפרויקט KolZchut-offline או בפרויקטים דומים | גבוה |
| יכולת טכנית | יודע להריץ Python מקומי, משתמש ב-git/gh או מוכן ללמוד | גבוה |
| כוונות טהורות | רוצה לעזור לקהילה, לא למטרות רווח/נזק | קריטי |
| זמינות | מוכן לבדוק עדכונים מעת לעת (לא חייב יומי) | בינוני |

**המלצות:**
- התחל עם 2–4 עדכנים מורשים בלבד. קל להרחיב בהמשך.
- עדיף לבחור אנשים שכבר תרמו בעבר (המלצה, דיווח באג, בדיקה).
- אם יש ספק — אל תוסיף. עדיף פחות עם יותר אמון.

## 6. תהליך הוספת עדכן מורשה

לאחר קבלת הודעה פרטית והסכמה:

1. **אימות בסיסי:** בדוק שה-GitHub username תקין, וודא יש לו חשבון פעיל.
2. **הוספת Collaborator בריפו:**
   - GitHub Repo → Settings → Collaborators and teams → Invite
   - הזן username
   - הרשאה: `Write` — היא ההרשאה המינימלית שמאפשרת לדחוף ענף משלו. היא **לא**
     מאפשרת דחיפה ל-master: הענף מוגן (required check `verify`, בלי דחיפה ישירה,
     כולל למנהלים). אל תיתן `Admin`.
   - שלח הזמנה.
3. **עדכן את הרשימה הפנימית** (לא חובה לפרסם) של מי מורשה.
4. **שלח הודעה פרטית עם הוראות ההפעלה** (ראה סעיף 7).
5. **וודא הבנה:** בקש שיבדקו שההזמנה התקבלה ושהסקריפט רץ לראשונה.

> **חשוב להסביר למעדכן:** עדכוני *תוכן* ממוזגים אוטומטית. שינוי בקוד, בסקריפטי
> האימות או ב-workflows **לא** ממוזג אוטומטית — הוא ממתין למיזוג אנושי. זה מכוון:
> אחרת אפשר היה להחליף את מנגנון הבדיקה דרך PR ולעקוף את השער.

## 7. מה לומר לעדכן מורשה בהודעה פרטית

העתק טקסט זה לעריכה:

```text
שלום,

אתה מוזמן להצטרף כעדכן מורשה של KolZchut-offline.

איך זה עובד בקצרה:
1. מריצים kolzchut_contribute.py מהמחשב המקומי
2. הוא בודק עדכונים, יוצר ענף ו-Pull Request
3. אם כל הבדיקות עוברות — המיזוג קורה אוטומטי

שלבים ראשוניים:
1. קבל/אשר את ההזמנה לקולבורייטור בריפו: https://github.com/Lev-Good/KolZchut-offline/invitations
2. שכפל את הריפו למחשב המקומי (git clone) או עדכן מקומי קיים
3. התקן dependencies: `pip install -r requirements.txt` (requests, beautifulsoup4)
4. הרץ פעם ראשונה: python kolzchut_contribute.py --help (להיכרות)
5. להרצת עדכון רגילה: python kolzchut_contribute.py
   - הסקריפט יבצע סנכרון דלתא, יוודא הרשאות, יצור branch+PR עם התווית auto-merge-candidate
   - אם הכל תקין, PR ייפתח אוטומטית

אבטחה:
- אל תריץ קוד זר. הרץ רק את הסקריפטים מהריפו המאושר.
- אל תדחוף ל-master ישירות — זה חסום.
- כל עדכון עובר בדיקות CI אוטומטיות לפני מיזוג.
- אין מפתחות/טוקנים משותפים בקוד.

שאל אותי אם משהו לא ברור. בהצלחה.
```

## 8. תרחישים לבדיקה עם עדכן מורשה (מומלץ לפני הפצה רחבה)

בצע לפחות אחד מהתרחישים הבאים עם עדכן מורשה אמין:

| תרחיש | מטרה | צפי |
|---|---|---|
| הצלחה | עדכון תקין קטן | PR נפתח, PR-check עובר, מיזוג אוטומטי, Release מופעל |
| כישלון מבוקר | שינוי עם בעיה (למשל index לא תקין) | PR נפתח אך PR-check נכשל — המיזוג לא קורה, דוח שגיאות מוצג |
| התנגשות | master השתנה מאז תחילת סנכרון | contribute מזהה או auto-merge חוסם (mergeStateStatus DIRTY) ודורש ריצה מחדש |
| עדכון כפול | הרצה כפולה ללא שינוי | לא יפתח PR מיותר או ינקה בצורה בטוחה |
| מחיקה חריגה | יותר מ-1% מהארכיון מסומן למחיקה | PR-check חוסם מיזוג (אנומליה) |

**כלי בדיקה:** `kolzchut_verify.py` תמיד חייב להחזיר exit 0 על הארכיון הנוכחי. `docs/DISTRIBUTED_UPDATES.md` מכיל פירוט נוסף.

## 9. כללי הפצה מומלצים

- **מתחילים קטן:** פרסם פוסט ראשון עם הטקסט לעיל. אל "פותחים" לכולם — רק מי שפנה בפרטי.
- **שקיפות:** הסבר שהמערכת עובדת אוטומטית לאחר בדיקות, ואין צורך באישור ידני ממך.
- **אבטחה מעל נוחות:** עדיף לדחות בקשה מאשר לקבל עדכן חשוד.
- **תיעוד:** שמור רשימה פנימית של עדכנים מורשים (username + תאריך הוספה). לא חובה לפרסם.
- **גיבוי ידע:** ודא לפחות עוד אדם אחד מכיר את התהליך למקרה חירום.
